# Database Specification

**Project:** Film Transcript Tool

**Status:** Draft

**Version:** 0.1

---

# 1. Purpose

This document defines the persistent data model for Film Transcript Tool.

The database stores:

- users
- projects
- media organization
- videos
- transcripts
- transcript editing data
- comments
- processing state

The database uses PostgreSQL.

---

# 2. Database Principles

## Relational First

Core application data should use relational tables.

JSON fields may be used for:

- external API responses
- provider-specific metadata
- flexible configuration data

---

## Preserve Source Data

Imported data should not be destroyed.

Examples:

- Original video files remain unchanged.
- Original transcript information is preserved.
- User edits are stored separately.

---

## Ownership

User-owned content should always have a clear ownership relationship.

# 5. Project Membership

Projects support multiple users.

## Fields

```
id

project_id

user_id

role

created_at
```

`role` is one of `owner`, `editor`, or `viewer`. Every project has at least one
owner; a project's creator is granted `owner` on creation. `owner` and
`editor` may create/edit/delete content; `viewer` is read-only. Only an
`owner` can invite members, change roles, or remove members, and a project
must always retain at least one `owner` (the last owner cannot be demoted or
removed).

# 12. Transcript Token

Tokens are the smallest editable transcript unit.

Initially each token represents a word from the transcription provider.

## Fields

```
id

transcript_id

segment_id

original_text

edited_text

start_time

end_time

is_deleted

version

created_by

created_at

updated_by

updated_at
```

`version` is an optimistic-locking counter starting at 1, incremented on every
edit/delete/merge/split of that row. A replacement token created by a merge
or split starts at version 1 (it is a new row, not a continuation of the
original's version history).

---

## Token Rules

Displayed text:

```
edited_text if present

otherwise

original_text
```

A token may be:

- edited
- deleted
- replaced by merged tokens
- replaced by split tokens

## Concurrency

Every write (edit/delete/merge/split) requires the caller to supply the
`version` it last read for each token it is modifying. If the current
`version` in the database no longer matches, the write is rejected with a
conflict rather than applied — two users editing the same token never
silently overwrite one another.

Deleted tokens remain stored.

# 16. Processing Job

Represents asynchronous processing.
Processing jobs are stored in PostgreSQL and act as the application queue.
Workers claim jobs using database locks.

Examples:

- proxy generation

- translation

id

type

status

progress

error_message

created_at

started_at

completed_at
```

Statuses:

```

 |

 |
 |-- Folder
 |     |
 |     |-- Folder
 |     |
 |     |-- Video
 |
Video
 |
 |-- Video Assets
 |
 |-- Speakers
 |
 |-- Transcripts
	   |
	   |-- Segments
			 |

---

# 19. Data Not Stored

The database does not store:

- original video binary data
- proxy video binary data
- generated waveform binary data

These belong in storage.
