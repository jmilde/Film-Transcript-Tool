# User Management & Edit-Conflict Safety — Implementation TODO

Persistent, git-tracked checklist for adding project roles, member invites, and
optimistic-locking on transcript token edits. Stands alongside `TODO.md`
(read `backend/CLAUDE.md` and the repo-root `CLAUDE.md` first — same rules
apply: fully typed, `mypy --strict` clean, ruff clean, TDD, test tree mirrors
source tree, explicit imports, autogenerated migrations only).

Confirmed decisions (see conversation record for rationale):
- Roles: **Owner / Editor / Viewer** on `ProjectMembership`. Enum named
  `MembershipRole` (not `ProjectRole`) and membership-check helpers kept
  composable so a future `Organization` layer (multi-tenant orgs owning
  projects) can reuse the same shape later — no org work happens here.
- Conflict strategy: **optimistic locking**. A `version` counter on
  `TranscriptToken`, checked on every write (edit/delete/merge/split);
  mismatch -> `409 CONFLICT` carrying the current server-side token state.
  Never silently auto-refresh a client on conflict.
- Invite model: an invited user must already have signed in at least once
  (matches the existing JIT-provisioning in `core/auth.py:get_current_user`,
  which only creates a local `User` row on that user's first authenticated
  request). No email-sending / pending-invite system in this pass — inviting
  an email with no local `User` row yet returns a clear 404 telling the
  inviter the person needs to sign in first. A pending-invite system is a
  reasonable future extension, not built here.
