## Context (see the plan file for full detail)

The chat agent has one tool, `search_transcripts(query: str)`
(`backend/app/agents/transcript_search.py`), backed by `search_chunks()`
(`backend/app/services/chat_retrieval.py`). Today it always: embeds `query`
for an ANN (pgvector) leg capped at `ANN_CANDIDATES=20`, runs the same
`query` as Postgres FTS capped at `FTS_CANDIDATES=20`, unions both by chunk
id, reranks the union against `query` with an external cross-encoder, returns
a fixed top `RERANK_TOP_K=8`. No relevance threshold anywhere. One query
string does embedding, FTS, and reranking duty, and there's no way to scope a
search to a speaker/video/folder — which pushes the model toward folding
entity names into the search text, actively hurting reranking (a real match
can get penalized for not textually repeating a name that was never a
text-content fact).

Confirmed decisions (see the design record for the "why" behind each — do
not re-litigate these while implementing):

- **No hard cutoff on the final reranked list shown to the model** — expose
  the rerank score instead, let the model reason about weak-but-real matches.
- **A cosine-distance cutoff on the raw ANN leg is still wanted** — a
  pre-rerank recall-quality filter, not the same thing as the point above;
  both coexist.
- **One tool, two optional query params** (`fts_query`, `semantic_query`),
  not two separate pydantic-ai tools.
- **Structural filters** (`speaker_name`, `video_id`, `folder_id`) are
  completely separate from query text — never let the model fold identity
  facts into `fts_query`/`semantic_query`.
- **A new `lookup_entities` tool** resolves a name/title fragment to an exact
  speaker name / video id / folder id before a scoped search.
- **All tool calls stream to the UI**, both call-start and call-result
  (short outcome summary), for both tools.
- **`MAX_SEARCH_TOOL_CALLS`: 4 → 10**, with prompt guidance to spend the
  budget economically (cheap FTS-only calls can run several times with
  varied phrasing; semantic/embedding calls are costlier, use deliberately).

No schema/migration changes are needed anywhere in this checklist —
speaker filtering uses the existing denormalized `TranscriptChunk.speaker_name`
string column; video/folder name lookup uses `ILIKE`, not new FTS columns.

- [x] Restructure `search_transcripts`'s signature and docstring:
  ```python

  def search_transcripts(
      ctx: RunContext[ChatDeps],
      fts_query: str | None = None,
      semantic_query: str | None = None,
      speaker_name: str | None = None,
      video_id: uuid.UUID | None = None,
      folder_id: uuid.UUID | None = None,
  ) -> list[ChunkResult]:
      """Search the project's transcripts for passages about a topic.

      Provide at least one of `fts_query`/`semantic_query`; both may be given.

      - `semantic_query`: a natural-language phrase or sentence describing

        matched by meaning, works across languages and paraphrases.
      - `fts_query`: literal keyword(s) you expect to appear verbatim, e.g.

      Each result includes `relevance_score` (a relative confidence signal
      for this result set, not an absolute cutoff — a low score can still be
      a real, if weak, match) and `matched_via` (which leg(s) — "semantic"
      and/or "fts" — found it).
  ```
